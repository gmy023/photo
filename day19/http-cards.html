① 请求四件套

一次请求包含：方法 + URL + 请求头 + 请求体。 响应包含：状态码 + 响应头 + 响应体。

GET /api/clothes HTTP/1.1
Host: localhost:8000
Authorization: Bearer ***

② 请求方法

GET 查 ｜ POST 新增 ｜ PUT/PATCH 改 ｜ DELETE 删

GET    /api/clothes
POST   /api/clothes
PATCH  /api/clothes/3
DELETE /api/clothes/3

③ 状态码速记

2xx 成功：200 OK / 201 Created
4xx 你的锅：400 参数错 / 401 未登录 / 403 无权限 / 404 不存在
5xx 服务器的锅：500 内部错误 / 502 网关错 / 503 服务不可用

④ Cookie vs Token

Cookie：浏览器自动携带，适合传统网页。
Token(JWT)：前端自己存（localStorage），每次手动放请求头，前后端分离项目主流。

Authorization: Bearer <token>

⑤ 跨域 CORS

协议/域名/端口不同 = 跨域，被浏览器拦截。解决靠后端在响应头声明允许的来源：

Access-Control-Allow-Origin: http://localhost:5173

⑥ RESTful 命名

用名词 + 方法表达动作，不用动词拼接口名。

✅ GET /api/clothes
✅ DELETE /api/clothes/3
❌ /api/getClothes
❌ /api/deleteCloth?id=3

📒 AI 衣橱 · 6 个 RESTful 接口设计

接口清单

  1. GET /api/clothes —— 获取衣橱列表
  2. POST /api/clothes —— 新增衣物
  3. PATCH /api/clothes/:id —— 修改衣物信息（如改价格）
  4. DELETE /api/clothes/:id —— 删除衣物
  5. POST /api/outfits/suggestions —— 获取 AI 搭配建议
  6. POST /api/auth/login —— 用户登录

思考题：为什么"AI 搭配建议"适合用 POST 而不是 GET？
GET 的参数拼在 URL 上，有长度限制还会被记录在历史里； 而搭配建议需要携带衣橱清单、场合、天气等可能很长的数据， 放进 POST 的请求体里更安全、也没有长度顾虑。

一句话总结（401 vs 404）： 401 是"你没带通行证"（未登录/凭证无效），404 是"这个地址上没有你要找的东西"（资源不存在）。
